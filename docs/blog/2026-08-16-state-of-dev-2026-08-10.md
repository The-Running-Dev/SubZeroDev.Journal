# State of Dev

## Week of August 10, 2026

The Game Engine was already working.

This week I made the mistake of asking what else it could be used for.

The answer included reusable scenes, remote content synchronization, embedded quests, tutorials that are themselves games, development workflows represented as graphs, restaurant ordering systems, community-authored campaigns, and enough telemetry to discover exactly how much AI it takes to make all of this happen.

Meanwhile, Git Service started hosting the repository containing Git Service, SkynetHR connected to its backend, and Patreon became a perfectly reasonable thing to set up.

Normal progress.

# Executive Summary

The largest shift this week was in Adventures and the Game Engine content model.

Campaigns are no longer looking like monolithic authored graphs. The emerging model is smaller reusable scenes that can be published independently, composed into different campaigns, synchronized remotely, extended at runtime, and eventually shared through a community content system.

That changes authoring substantially.

Instead of asking someone to build an entire adventure, the platform can let them create one scene, publish it, and allow that scene to become part of many different experiences.

The second major theme was convergence.

The Game Engine is becoming useful for things that are not obviously games. Tutorials, deployment workflows, menu ordering, interactive landing pages, and embedded website experiences can all use the same graph mechanics.

The third theme was infrastructure catching up with development velocity.

A telemetry review showed that AI usage varies dramatically between repositories, AgentKit's current documentation workflow is consuming too much context, and several repositories still lack the context-warning tooling already used elsewhere.

Apparently the next optimization target is the development process itself.

## Game Engine and Adventures

The engine itself is no longer the interesting constraint.

Authoring is.

The biggest idea this week was to stop requiring people to create complete campaign graphs and instead let them build individual scenes.

A scene can contain its own content, questions, outcomes, and achievements. Scenes can then be public or private and composed into different campaign graphs.

Existing campaigns can be decomposed into reusable pieces, which also creates a starter library for anyone building new experiences.

This solves several problems at once:

- authoring becomes smaller and less intimidating;
- content becomes reusable;
- community contributions no longer require understanding an entire campaign;
- the same scene can appear in multiple stories;
- private and public content can coexist.

The usual problem occurred.

A simpler editor created a larger platform.

## Remote Content and Synchronization

Adventures gained a stronger remote-content model.

Campaigns and extensions can be loaded from URLs, pasted directly, or synchronized from the dedicated content repository.

The next obvious step is a webhook from the content repository deployment into the API so new content can be synchronized automatically.

The blog can eventually participate in the same system.

A post can be converted into story content, published with the correct manifest, and then discovered by Adventures without manually moving files between systems.

The blog was supposed to contain words.

It is now apparently a game-content provider.

## SkynetHR

SkynetHR crossed an important line this week: it connected to a real backend.

Sign-in works.

Save and restore work.

Data can be stored and retrieved.

The next layer is agent interaction, including replies, personalities, MCP control, and eventually voice.

Personality support is also becoming unnecessarily specific.

Future agents may be cheerful, grumpy, Lucifer-like, or modeled after a permanently dissatisfied Hungarian coworker.

Enterprise software has finally found its true purpose.

## Git Service

Git Service continued toward a deliberately recursive architecture.

The service can host a Git repository.

That repository can contain the code for Git Service.

Git Service can therefore host the repository containing the code for the service currently hosting the repository.

There is no architectural problem here.

There is merely a diagram nobody should draw.

# New Concepts and Ideas from the Week

## Scene-First Authoring

The scene builder is probably the most important product idea of the week.

Campaign creation changes from:

"Build a graph."

to:

"Build a scene."

Scenes can then be combined into graphs later.

This also makes community contribution considerably more practical. Someone can contribute one ridiculous encounter without needing to understand the entire engine.

## Achievements From Completed Quests

Achievements already exist at the engine level.

The new idea is to generate or expose achievements specifically from completed quest content.

That gives each adventure a stronger sense of identity and produces another useful piece of post-game data.

Naturally, some achievements should probably commemorate decisions no reasonable achievement system would normally recognize.

## Post-Game Feedback and Discussion

The Adventures platform needs a layer after the game ends.

Ideas include:

- feedback links;
- discussion around individual adventures;
- play statistics;
- playtime;
- deliberately absurd statistics;
- achievement summaries.

The lack of visible response to the Bulgarian Adventures Reddit post made this considerably more interesting.

The post reached roughly 1,200 views with effectively no public discussion.

Which means "nobody commented" tells almost nothing about whether people actually played anything.

Telemetry does.

## Interactive Landing Pages

The Game Engine can itself explain the Game Engine.

Instead of a conventional landing page, a visitor can move through an interactive graph describing what the product is, why it exists, and how it works.

The same approach can be used for Adventures and the wider platform.

There should, of course, be a "Skip Intro" option.

Skipping it should probably unlock an achievement.

## Embedded Quests

Because the engine runs in the browser and can consume remote JSON, an adventure can be embedded inside another website.

Build the quest in Adventures.

Publish it.

Apply a custom skin.

Embed it elsewhere.

The engine quietly becomes an interactive-content framework.

## Tutorials As Gameplay

Documentation and onboarding can use the same mechanics.

Instead of explaining how to use Adventures through a conventional tutorial, the tutorial itself can be an adventure running inside the engine.

The user learns the system by using the system.

This is recursive enough to qualify as official SubZeroDev architecture.

## Workflows As Graphs

The graph model also maps surprisingly well to development workflows.

Installation, deployment, repository setup, or automation processes can be represented as graph-driven experiences rather than static documentation.

This creates another category that is technically not a game while behaving exactly like one.

## Menu Ordering

A React Native menu-ordering system can also use the engine.

Products become choices.

Modifiers become branches.

Validation becomes state.

Checkout becomes an ending nobody wants to call an ending.

At this point, arguing about whether something is a game appears less useful than asking whether it can be represented as state plus transitions.

# Architecture and Technical Decisions

## Content Should Be Independently Deployable

Campaign content is moving further away from application deployment.

The dedicated Adventures.Content repository can publish content independently, while Adventures synchronizes or consumes it remotely.

This keeps content releases separate from application releases.

The planned webhook closes the loop by notifying the API whenever the content repository changes.

## Scenes Should Be Reusable Units

The campaign should not be the smallest authoring unit.

Scenes should.

Campaigns become compositions of reusable scenes rather than giant authored objects.

This is a substantial change to the authoring model but not to the deterministic engine underneath it.

That is exactly where the change belongs.

## Runtime Extensions Need Visible Boundaries

When a new scene or extension appears inside an existing campaign, the game should acknowledge it.

Ideas included transitions such as:

"The void. You shouldn't be here."

or:

"You've discovered a glitch in the Matrix."

This is partly presentation, but it also provides an explicit boundary between base content and dynamically injected content.

## Git Remains the Integration Layer

Content repositories, deployments, Git Service, MCP workflows, and automated synchronization continue converging around Git.

This is not because Git was selected as a universal application architecture.

It is because every time another integration problem appears, Git is already standing there.

## AgentKit Needs Less Documentation Reconciliation

A repository-level usage analysis exposed a major development-process issue.

The expensive part is not necessarily generating code.

It is repeatedly loading, comparing, reconciling, and updating large Markdown design documents that drift away from implementation contracts.

AgentKit needs a model where issues, contracts, and implementation state remain synchronized without requiring a high-end model to repeatedly rediscover the entire project's history.

The current process works.

It is simply making a small bonfire out of tokens.

## Telemetry Must Be Everywhere

The existing context warning is only wired into 7 repositories.

Eleven repositories have no equivalent warning.

The analysis showed that those 11 repositories represented only about 8 percent of measured sessions but consumed roughly 37 percent of all tokens.

That is not subtle enough to ignore.

Telemetry and context warnings need to become default infrastructure rather than optional repository upgrades.

# Notable Accomplishments

Bulgarian Adventures was completed well enough to publish publicly on r/bulgaria.

The post reached roughly 1,200 views.

The Adventures content architecture now supports remote sources, pasted content, campaign extensions, and full campaigns.

The dedicated content repository is functioning as the natural source for independently deployed campaigns.

The scene-builder direction was defined.

The engine gained several credible non-game use cases without requiring changes to its fundamental mechanics.

SkynetHR connected its UI to persistent backend functionality.

Git Service reached the point where recursively hosting its own repository became a legitimate architectural observation rather than a joke.

The API and Adventures infrastructure are already behind Cloudflare, which also means some resilience and CDN behavior arrived almost accidentally.

The AI usage audit produced an actionable optimization target rather than another vague feeling that some sessions were expensive.
